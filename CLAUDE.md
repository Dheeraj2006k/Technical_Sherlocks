# Sherlock's Last Case

Browser-based detective game (SQL track + Logic track) for a one-day techfest. Next.js (App Router, TypeScript) on Vercel + Supabase Postgres. Spec: docs/PRD v5 (docs/PRD__Sherlocks_Last_Case-_v5.pdf). Status and honest gaps: docs/IMPLEMENTATION_STATUS.md, docs/PRD_V5_GAP_ANALYSIS.md, docs/ASSUMPTIONS_AND_DECISIONS.md.

## Hard rules (never break)
- NEVER use the Supabase service-role key or any RLS-bypassing role to run player SQL or Evidence Browser queries. Both go through `lib/playerdb.ts` as the low-privilege `player_exec` login only.
- team_id, role, case_id are derived ONLY from the signed server session (and re-checked in the DB), never from client input. Phase, unlocks, hints, points and results are server-owned and never taken from a request body.
- Scoring, thread completion, phase advance and finishing happen in ONE transaction under the team's `team_progress` row lock (`lib/engine.ts`). Every scoring endpoint is idempotent (idempotency keys; one completion per team and question).
- Secrets (DATABASE_URL, DATABASE_URL_PLAYER, service key, SESSION_SECRET, ADMIN_PASSWORD) are server-side only. Never NEXT_PUBLIC_, never committed, never logged, never printed. Never read or print `.env.local` values.
- No AI or fuzzy grading anywhere. Exact-match grading only (`lib/game.ts`).
- Use SET LOCAL / `set_config(..., true)` (never plain SET) because we use the transaction-mode pooler.
- Tests, seeds, resets and migrations run against the LOCAL embedded Postgres (`npm test`). Tooling refuses a remote database unless `SLC_ALLOW_REMOTE_DB=1`. Do not run migrations, seeds, resets or destructive tests against the real database, and do not commit, push, deploy or change Vercel/GitHub settings, without explicit approval.
- Do not weaken RLS, authentication or the SQL restrictions to make something pass, and do not delete tests because they fail.

## Workflow
- Plan first, then build. A change is done only when lint, `npx tsc --noEmit`, `npm run build`, `npm test` and `npm run check:leaks` pass; report failures honestly.
- If the PRD is ambiguous, choose a reasonable option, record it in docs/ASSUMPTIONS_AND_DECISIONS.md, and ask only when the choice is material or affects production.

## Design rules that are easy to break
- **Registration first.** Organizers create `registrations` and assign a case (`team_case_assignments`, audited). The head joins with registration reference + the ASSIGNED case code + case password; the case comes from the assignment, never from what the head claims. All credential failures return the same 401 with a dummy bcrypt compare. One team per registration (unique index); a repeated or concurrent head join returns the existing head.
- **Codes.** `cases.case_code` is a catalogue code (`SQL01`..`SQL10`, `LOG01`..`LOG10`), normalized only by trimming/upper-casing (never O->0 substitution). Registration reference (8) and team code (6) are Crockford base32, generated with crypto.randomInt, normalized (O->0, I/L->1, hyphens, case) before lookup. Only `published` cases are joinable or assignable.
- **Credentials never leak.** Case passwords, case ids, registration references and gate keys must not appear in any player-facing response, log line or cookie. The public leaderboard shows no ids, codes or team codes.
- **One evidence gate.** Each evidence table in `case_<slug>` has its own secret key in `case_table_keys` (server-only); its RLS policy holds only the SHA-256 of that key. The server computes the team's unlocked tables (`getUnlocks` in `lib/engine.ts`: phase tables + thread tables unlocked when a thread is available or complete) and sets `app.keys` to those tables' keys inside the read-only transaction. The SQL console and the Evidence Browser BOTH use this path; never add a second one. Do not use `SET ROLE` or case-keyed GUC designs: they are defeated from inside a single SELECT.
- **Evidence Browser** (`/api/evidence`): table and column names come from an allow-list of the real columns of unlocked tables; every value is a bound parameter; LIKE wildcards are escaped; nothing from the request is concatenated into SQL.
- **Player SQL rules**: one read-only transaction per query; pg-cursor (extended protocol, exactly one statement) reading at most 201 rows; `statement_timeout` 3s plus a 6s wall-clock deadline; the checked-out client always has an `error` listener and is destroyed after any failure; `player_exec` has no grants on `public`. The pre-check also refuses catalog/metadata queries (`pg_*`, `information_schema`, ...) as a usability layer (Postgres cannot hide catalog rows per team: documented limit).
- **Scoring**: every case totals exactly 100 (8 questions x 10 + responsibility 12 + explanation 8). Reward by hints used 10/8/6/4/2. Wrong answer (question or final): -2, never below zero, retries allowed. Hints are shared by the team, opened in order, idempotent per position. A thread completes when all its questions are done; a phase advances when all its REQUIRED threads are done; a required thread never depends on an optional one (solo players must always be able to finish). The case closes only when BOTH final components are resolved.
- **Rate limits are DB-backed** (no in-memory counters; Vercel is serverless): answers 10 per player per minute (from `task_attempts`), final guesses 10 per team per minute, console 30 per player per minute (`query_logs`), Evidence Browser 90 per player per minute, join 10/min and 30/hour per IP (HMAC of the IP), admin login per IP.
- **Leaderboards** are per track (SQL / LOGIC): total points, then earliest completion of the final deduction (`teams.finished_at`), then earliest start.
- **Realtime**: Supabase Realtime "changed" pings on channel `team:<teams.realtime_token>`; pings carry no data; clients refetch /api/state; the service key is used ONLY to publish pings; without realtime the UI polls every 3s (tested).
- **Admin**: password-gated, signed `slc_admin` cookie (audience-bound, SameSite=Strict, origin-checked POSTs), login rate-limited. Every reassignment, reset, delete and registration batch is written to `admin_audit` (actor label `organizer`). Reset modes: "state" (wipe progress, keep players/code/assignment) and "delete" (remove team, kill sessions, assignment returns to `assigned`). Emergency pause is per team or global; paused teams cannot query, submit, hint, start or finish and their timer is frozen.
- **Cases**: 20 definitions in `scripts/cases/` (`index.mjs`): SQL01-10 from `skeleton-a.mjs` + `themes.mjs` (+ hand-authored Opening Night) via `to-v5.mjs`; LOG01-10 from `skeleton-b.mjs` + `themes-b.mjs`. `scripts/cases/engine.mjs` installs and validates them. `node scripts/verify-case.mjs` mechanically checks answers, uniqueness, scoring, structure and solo-solvability; it does NOT replace a human who does not know the answers playing each case.
